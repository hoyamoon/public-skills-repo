# Dev Evidence Gate — 증거 기반 완료 규율

> 코드 작업의 완료는 주장이 아니라 **캡처된 증거**로 선언한다. "이렇게 하면 될 것이다"·"타입이 맞는다"·"테스트가 초록이다"는 각각 추측·형식 검사·작성자가 예상한 범위일 뿐, 사용자가 보는 표면에서 동작함을 증명하지 않는다.

## 0. 적용 범위·강도

- **대상**: 코드 산출물이 남는 모든 작업. 앱·사이트·스크립트·자동화·CLI 도구·빌드 설정 등.
- **비대상**: 글·슬라이드·문서 등 콘텐츠 산출물(→ work-harness §4 하네스 체크리스트).
- **상속**: 개발 계열 스킬은 본문에 "dev-evidence-gate 적용" 한 줄로 이 규율을 상속하고, 스킬 고유의 완료 기준만 자체 정의한다.
- **강도 조절**:
  - **전체 적용** — 사용자가 "빡세게"·"제대로 검증"·`ulw`라 말했거나, 다중 파일 변경·리팩터·마이그레이션·보안·인증·결제·DB 스키마 작업일 때. §1 시나리오 3개 이상 + §6 리뷰어 루프.
  - **축소 적용** — 한 지점 버그픽스, 설정 한 줄, 기존 패턴을 그대로 따르는 단순 추가. §1 시나리오 1~2개, §6 생략, §2~§5는 그대로 유지.
  - 애매하면 전체 적용을 고른다. 작업 도중 전체 적용 조건이 드러나면 즉시 승급하고, 축소 적용이 건너뛴 부분을 소급해 채운다. 강등은 하지 않는다.

---

## 1. 시나리오 계약 (착수 전 — 구속력 있음)

코드를 쓰기 **전에** 이번 변경이 통과해야 할 시나리오를 확정하고 작업 메모에 기록한다. 이 계약이 완료 판정의 유일한 기준선이다.

| 종류 | 필수 여부 | 예 |
|---|---|---|
| 정상 경로 | 항상 | 유효 입력 → 200 + 기대 본문 |
| 엣지 (경계·빈 값·비정형·동시성) | 위험 작업 시 | 빈 목록, 동시 쓰기 2건, 잘못된 형식 |
| 인접 표면 회귀 | 다중 파일 변경 시 | 기존 호출처 X가 여전히 동작 |

각 시나리오는 세 가지를 **리터럴로** 명시한다:

1. **판정 조건**: 이진 관찰 가능. "200 반환 + body가 스키마 일치"처럼. "동작해야 함"·"제대로 나오면 됨"은 시나리오가 아니다.
2. **정확한 호출**: 실행할 명령·액션 그대로. `curl -i http://localhost:3000/login`, `page.click('.login-button')`, `python3 script.py --dry-run=false`. "엔드포인트 실행해보기"는 호출이 아니다.
3. **증거 아티팩트**: 무엇을 캡처할지. 상태줄+본문, 스크린샷 경로, stdout, DB 상태 diff.

## 2. 증거 2종 (완료의 필요조건)

### 2.1 실패우선 증명 (RED→GREEN)

- 동작을 바꾸는 변경은 **구현 전에 실패를 캡처**한다. 가장 값싼 충실한 채널로: 이음새가 있으면 단위 테스트, 배선에 있으면 통합·e2e 테스트, 테스트 이음새가 없으면 §1 시나리오 자체를 실패 상태로 캡처.
- 실패는 **올바른 이유**로 실패해야 한다. 문법 오류·임포트 누락 때문에 난 실패는 무효다.
- 구현 후 같은 증명을 통과 상태로 재캡처한다. **구현 후에 추가한 테스트는 이 증명을 대신하지 못한다.**
- GREEN을 만드는 데 예상보다 훨씬 큰 변경이 필요했다면 증명이 너무 거칠었던 것이다. 시나리오를 쪼갠다.
- 면제 화이트리스트: 순수 포맷팅, 주석만 변경, 동작 변화 없는 의존성 범프, 이름만 바꾸는 이동. 면제는 사유를 기록한다.
- 이미 올바른 동작에 회귀 커버리지만 추가하는 경우에는 자연 RED가 없다. **변이 증명**으로 대체한다. 해당 회귀를 일부러 일으켜(수정 커밋 되돌리기, 이음새 깨뜨리기 — 커밋하지 않음) 단언이 실패하는 것을 캡처한 뒤 되돌린다. 변이에도 초록인 단언은 커버리지가 아니다.

### 2.2 실서피스 수동 QA

**테스트 통과 ≠ 완료.** 완료 선언 전에 사용자가 실제로 쓰는 표면에서 직접 한 번 써 본다.

| 산출물 표면 | 검증 채널 | 캡처 |
|---|---|---|
| CLI·스크립트 | 실제 실행 (정상 경로 + 비정상 입력 1개 + `--help`) | stdout / exit code |
| TUI·터미널 앱 | 실제 터미널 구동 | 렌더 출력·전사 |
| 웹 UI | 실제 브라우저 구동 (Playwright 등) | 액션 로그 + 스크린샷 |
| HTTP API·서비스 | 살아있는 프로세스에 `curl` | 상태줄 + 헤더 + 본문 |
| 라이브러리·모듈 | import해서 끝까지 실행하는 드라이버 스크립트 | 실행 출력 |
| 데이터·설정 산출물 | 파싱·적용 결과 diff | DB / 설정 상태 diff |

- `--dry-run`, "명령을 출력해봄", "응답할 것임", "코드를 읽어보니 맞음"은 증거가 아니다.
- 사용 중 발견한 결함은 이번 작업 범위다. 즉시 고치고 해당 시나리오만 재검증한다.

### 2.3 보조 신호 (필요하지만 충분하지 않음)

빌드 exit 0, 테스트 스위트 초록, 린트·타입 진단 클린. 변경 파일에 대해 통과해야 하지만, 이것만으로 완료를 선언할 수 없다.

## 3. 프로즈 산출물 예외 (프롬프트·문서·규칙 파일)

문구 자체는 행동이 아니다. 프롬프트·스킬 문서·규칙 파일 변경에는:

- **금지**: 문구 존재를 grep으로 잡는 인수 조건("이 문장이 파일에 있는가", 단어 수 검사). 그건 diff를 고정할 뿐 행동을 고정하지 않고, 이후의 정당한 편집을 전부 막는다.
- **허용**: ① 기계가 소비하는 값만 검증 — frontmatter 필드 파싱, 문서 안 JSON 예시를 실제 검증기에 통과, 설정 스키마 검사. ② 의도 대비 정독 리뷰(§6).
- 순수 프로즈 변경은 테스트 없이 리뷰 + 정독 QA로 출하한다.

## 4. 정리 영수증 (QA 잔여물 teardown)

QA가 리소스를 띄우는 순간 그 정리를 할 일 목록에 등록하고, 완료 선언 전에 정리를 확인해 한 줄 영수증으로 기록한다.

대상: 서버 프로세스(종료 후 확인), 터미널 세션, 브라우저·Playwright 컨텍스트, 컨테이너, 점유 포트, 임시 파일·디렉터리, QA 전용 환경변수.

**잔여물이 남아 있으면 완료가 아니다.** 영수증 예: `cleanup: 서버 pid 12345 종료 확인, 임시 경로 /tmp/qa.aB12 삭제 완료`.

## 5. 정지 규칙

- **완료 조건 성립 즉시 정지.** §1의 모든 시나리오가 증거와 함께 통과하고 §4 영수증이 기록된 순간이 끝이다. 그 뒤의 추가 검증 루프·재다듬기·보너스 리팩터링·지나가다 하는 정리는 성실이 아니라 **범위 초과 결함**이다.
- **동일 실패 2회** 후에는 재시도하지 않고 시도 내용·막힌 지점을 사용자에게 보고한다.
- **3연속 실패로 코드가 깨진 상태**면 편집을 중단하고 마지막 동작 상태로 되돌린 뒤 시도·실패를 기록해 보고한다. 깨진 상태로 방치하거나, 통과시키려고 테스트를 삭제·skip 처리하지 않는다.
- 완료를 추론으로 선언하지 않는다. 캡처된 증거로만 한다.

## 6. 위임·리뷰어 규율

### 6.1 위임 계약에 STOP WHEN·EVIDENCE 추가

코드 작업을 서브에이전트에 위임할 때 기본 위임 계약(역할·참조 문서·입력·산출물 경로·반환 형식·재위임 금지 — work-harness §9)에 두 필드를 더한다:

- **STOP WHEN**: 자식의 실행을 끝내는 **관찰 가능한 조건** 한 줄. 정지 조건 없는 자식은 목표를 지나쳐 배회한다.
- **EVIDENCE**: 자식이 반환해야 할 증거(§2의 캡처물).

**자식의 완료 판정은 self-report가 아니라 반환된 증거를 STOP WHEN에 대조해서 한다.** 메인은 자식이 만들었다고 주장한 파일을 직접 읽어 대조한다. 설명할 수 없는 변경은 검수한 것이 아니다.

### 6.2 리뷰어는 승인 편향 (blocker-finder)

검수 담당(사람이든 별도 에이전트든)에 적용하는 규율:

- 리뷰어의 질문은 하나다: **"이 산출물이 §1 시나리오·완료 기준을 깨는가?"** 기준을 깨는 것만 blocker다.
- 취향 차이("나라면 다르게 했을 것")·완벽주의·문체 지적은 blocker가 아니라 note다. 반영 여부는 작성자 재량.
- **반려 1회당 blocker 최대 3건.** 더 찾았어도 상위 3건만 올린다.
- 애매하면 승인한다. 같은 리뷰어 재제출은 **최대 2회**, 그때는 변경분 diff와 지난 blocker만 전달한다. 2회 후에도 blocker가 남으면 §5 정지 규칙대로 사용자에게 올린다.

> 리뷰어를 완벽주의자로 두면 무한 수정 루프가 생긴다. 리뷰어의 목적은 일을 막는 것이 아니라 막힌 곳을 뚫는 것이다.

## 7. 계획 인터뷰 2단 필터 (착수 전 질문 규율)

개발 작업 착수 전 사용자에게 물을 후보 질문마다 순서대로 거른다:

1. **탐색으로 답 가능한가?** 레포·문서·시스템에서 확인 가능한 사실(어디에 뭐가 있는지, 기존 패턴이 뭔지)은 묻지 않고 찾아서 인용한다.
2. **선언된 의도 + 방어 가능한 기본값으로 답 가능한가?** 되돌릴 수 있는 내부 구현 선택은 기본값을 채택하고 **채택 사실을 알린 뒤** 진행한다.

단, **오너 결정은 기본값이 있어도 반드시 질문한다**: 비가역·파괴적·보안 민감한 선택, 또는 사용자가 안고 살아야 할 횡단 선택(공개 설정 표면, 배포·패키징 방식, 외부 의존성 추가, 데이터·스키마 형태).

**의도 라우팅**: 결과물이 명확한 요청이면 살아남은 질문만 이유와 함께 묻는다. 결과 자체가 모호한 요청("알아서 좋게 만들어줘")이면 질문으로 일을 떠넘기지 말고 베스트 프랙티스 기본값을 조사·채택·공표한 뒤 §6 검수를 강화한다. 판단이 애매하면 명확한 요청으로 취급해 딱 1개만 묻는다. 잘못 침묵당한 사용자가 질문 1개보다 나쁘다.

## 8. 완료 보고 형식

완료 선언 시 시나리오별로 한 줄씩 보고한다:

```
S1 정상 경로 — PASS (curl 200 + body 일치, 증거: logs/s1-curl.txt)
S2 빈 입력 — PASS (RED→GREEN: test_empty_input)
S3 기존 호출처 회귀 — PASS (스위트 초록, 스크린샷: qa/s3.png)
cleanup — 서버 pid 12345 종료 확인, /tmp/qa.aB12 삭제
```

증거 없는 PASS는 쓰지 않는다.

## 부록. 설계 출처

이 스킬의 규율은 [oh-my-openagent](https://github.com/code-yeongyu/oh-my-openagent)(SUL-1.0)의 ultrawork·Hephaestus·Atlas 프롬프트에서 다음 아이디어를 차용해 재작성했다. 원문은 복제하지 않았다.

- 시나리오 계약과 이진 관찰 조건
- 실패우선 증명 + 실서피스 수동 QA의 증거 2종 구조
- 정리 영수증("QA가 남긴 것이 있으면 완료가 아니다")
- 정지 규칙("완료 조건을 넘어선 행동은 성실이 아니라 결함")
- 자식을 self-report가 아니라 증거로 판정하는 위임 규율
- 승인 편향 리뷰어("blocker를 찾는 사람이지 완벽주의자가 아니다")
