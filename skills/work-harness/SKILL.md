# Work Harness — 범용 작업 품질 하네스

두 가지로 쓴다.

1. **범용 워크플로우**: 전용 스킬이 트리거되지 않은 일반 작업을 §1~§2, §5~§6의 4단계로 처리한다.
2. **공통 표준 허브**: 다른 스킬이 동작 중일 때도 **§3 컨텍스트 레이어, §4 하네스 체크리스트, §7 금지어·문체, §8 규모 분류, §9 위임 계약, §10 적용 보고**를 병행 적용한다. 이쪽이 본질적 가치다.

> 다른 스킬에서 이 문서를 참조할 때는 섹션 번호로 참조한다 (예: "검수는 work-harness §4를 따른다").

---

## 1. 태스크 분류

요청을 받으면 아래 6가지 중 **주작업 1개 + 보조작업 0~1개**를 판정한다.

| 유형 | 예시 | 보조 결합 빈도 |
|---|---|---|
| writing | 이메일, 공지문, 짧은 제안 메모, 세일즈 한 단락 | persuasive·warm 톤 보조 |
| summarization | 문서·회의록·기사 요약 | analysis 보조 |
| planning | 짧은 기획안, 실행 계획, 체크리스트 | analysis 보조 |
| analysis | 비교, 평가, 장단점, 리스크 진단 | decision-support 보조 |
| transformation | 문체 변경, 번역, 형식 변환, 압축/확장 | — |
| decision-support | 선택지 추천, 우선순위, 판단 보조 | analysis 보조 |

판정이 모호하면 **사용자가 받아보고 싶은 결과물의 형태**를 기준으로 정한다. 예: "이걸 어떻게 결정할까?" → decision-support, "정리해줘" → summarization.

---

## 2. 실행 파이프라인

### Phase A — 설계

1. **목표 정의**: 사용자가 원하는 최종 결과물을 한 문장으로 확정한다.
2. **태스크 스테이트 수립**: 아래를 내부적으로 정리한다 (출력하지 않음).

```
task_type / document_type / audience / goal
tone / length / must_include / must_avoid
format / success_criteria
```

3. **구조 설계**: 결과물의 뼈대를 먼저 잡는다. 무엇을 먼저, 무엇을 나중에, 어떤 형식으로.

### Phase B — 생성 + 인라인 검증

초안을 만들면서 동시에 §4 하네스 체크를 수행한다. 통과하지 못한 항목은 **출력 전에 내부적으로 수정**한다 (검증 과정은 노출하지 않는다).

### Phase C — 출력

하네스를 통과한 최종본만 출력한다.

## 3. 컨텍스트 3레이어

긴 작업·멀티턴·복합 요청에서 컨텍스트 손실을 막기 위해 3개 레이어를 분리 유지한다.

| 레이어 | 내용 | 수명 |
|---|---|---|
| **Persistent** | 사실성, 구조 우선, 검증 후 출력, 과장 금지, 목적 우선 | 항상 |
| **Task** | 이번 작업의 문서 종류·독자·톤·길이·포함/금지 요소 | 작업 종료까지 |
| **Working** | 현재 진행 상태 — 뭘 만드는 중인지, 뭘 반영했는지, 뭐가 남았는지 | 단계 전환 시 갱신 |

**핵심 규칙**: 레이어를 섞지 않는다. Persistent 규칙을 Task 정보와 혼합하면 장기 작업에서 규칙이 희석된다. 예를 들어 "사실성 우선"이라는 Persistent 원칙이 "이번에는 임팩트 있게"라는 Task 톤 요청에 흡수되면 과장이 생긴다.

여러 세션에 걸치는 작업은 진행 상태(완료 단계·남은 단계·확정 사항)를 파일로 외재화하고 매 단계 완료 직후 갱신한다. 컨텍스트가 잘려도 그 파일에서 재개할 수 있어야 한다.

## 4. 하네스 체크리스트

출력 전 내부 검증. **각 항목은 객관적 판정 질문을 가진다.** 하나라도 실패면 출력 전 수정한다.

### 4.1 공통 6항목 (모든 작업)

| # | 항목 | 판정 질문 | 실패 신호 |
|---|---|---|---|
| H1 | 요청 커버리지 | 사용자 요청 문장의 모든 명시적 요소(주제·형식·분량·금지)가 결과물에 반영되었는가? | "분량 5줄"인데 10줄, 톤 지정 무시 |
| H2 | 즉시 사용 가능성 | 사용자가 그대로 복사·발송·실행할 수 있는가? "이걸 어떻게 쓰지?" 의문이 남는가? | 플레이스홀더가 본문에 남음, 추상적 다음 단계 |
| H3 | 일관성 | 톤·인칭·주장·구조가 처음부터 끝까지 충돌하지 않는가? | 앞에선 "추천", 뒤에선 "비추천" / 존댓말·반말 혼용 |
| H4 | 압축 내성 | 같은 정보를 더 짧게 쓸 수 없는가? 같은 말을 두 번 하지 않는가? | "효율적이고 효과적인" 같은 동의어 중복, 뻔한 배경 설명 |
| H5 | 정밀도 | 추상어("적절한", "효과적인", "다양한")를 구체 수치·예시·기준으로 바꿀 수 있는가? | "빠른 시일 내" → "3영업일 내" 변환 가능한데 안 함 |
| H6 | 사실 정합성 | 사용자 요청·제공 자료에 없는 단정·수치·인용이 들어가지 않았는가? 추측이면 추측으로 표시했는가? | 출처 없는 통계, "업계에선 보통…" 식 단정 |

### 4.2 다단계 작업 확장 2항목

| # | 항목 | 판정 질문 | 실패 신호 |
|---|---|---|---|
| H7 | 컨텍스트 정합성 | 이전 단계에서 확정한 사항·용어·구조를 그대로 이어받았는가? 임의로 바꾸거나 빠뜨리지 않았는가? | 1단계에서 정한 목차를 3단계에서 말없이 변경 |
| H8 | 환경·참조 유효성 | 실행 환경에서 실제로 동작하는 경로·도구만 썼는가? 참조한 파일·문서가 실존하는가? | 없는 파일 인용, 설치되지 않은 도구 전제 |

## 5. 안티패턴

- 막연한 칭찬·의미 없는 추상어로 분량 채우기
- 요청하지 않은 배경 설명 과다 삽입
- 사실 확인 없이 단정 ("일반적으로는…", "업계 표준은…")
- "그럴듯한 문장"에 집중하고 실행 가능성은 무시
- 기준 없이 장문 작성 (1,000자 넘는 결과물은 항상 H4 재적용)
- 한 문서에 서로 다른 톤 혼합
- 검증 과정·내부 사고를 출력에 노출

---

## 6. 유형별 핵심 규칙

- **writing**: 첫 문장에 핵심 목적 → 한 문단 한 메시지 → 톤 미지정 시 비즈니스 기본값
- **summarization**: 핵심 주장·근거·결론 분리 → 의사결정 정보 우선 → 한 줄 요약 / 핵심 포인트 / 실무 의미 3단
- **analysis**: 비교 기준 선정 → 주장+이유 세트 → 장단점 병기 → 조건부 결론
- **planning**: 목표→단계→산출물→리스크 순 → 담당자가 움직일 수 있는 단위 → 체크리스트 권장
- **transformation**: 원본 의미 보존 최우선 → 변환 전후 차이·손실 명시
- **decision-support**: 선택지별 장단점 병기 → 추천 시 조건·근거 명시 → 최종 판단은 사용자

## 7. 공통 금지어·문체 표준 (한국어)

### 7.1 금지어 6종

| # | 유형 | 예 | 대체 원칙 |
|---|---|---|---|
| 1 | 과장형 형용사 | 혁신적인, 획기적인, 완벽한, 최고의 | 구체 효과·수치로 |
| 2 | 모호한 부사 | 매우, 굉장히, 상당히, 쉽게, 빠르게 | 기준·비교값으로 |
| 3 | 근거 없는 단정 | ~할 수 있습니다(남용), 반드시 ~됩니다 | 조건부 서술로 |
| 4 | AI 흔적 상투구 | ~하는 것이 중요합니다, 다양한 방법이 있습니다, 결론적으로 | 삭제 또는 구체화 |
| 5 | 추상명사 남용 | 시너지, 패러다임, 솔루션(맥락 없이) | 실제 대상 명시 |
| 6 | 동의어 중복 | 효율적이고 효과적인, 명확하고 분명한 | 하나만 남김 |

### 7.2 금지 부호 — 긴 하이픈

본문 문장 안에서 긴 하이픈(em dash `—` / en dash `–`)을 쓰지 않는다. AI가 쓴 글에 자동으로 붙는 지문이고, 한국어 문장 부호 체계에도 자리가 없다.

| 원래 쓰임 | 대체 |
|---|---|
| 부연·환언 | 문장을 끊는다. 또는 쉼표·괄호 |
| 결론 앞의 호흡 | 마침표로 끊고 새 문장으로 |
| 목록 항목의 설명 구분 | 콜론(`:`) 또는 줄바꿈 |

적용 범위는 **독자에게 나가는 본문**이다(에세이·블로그·영상 대본·이메일 등). 이 문서 같은 지침·표·내부 주석은 제외한다. 검수 단계에서 `—`·`–` 문자를 직접 검색해 잔존 여부를 확인한다.

### 7.3 문체(종결어미) 결정 트리

1. **사용자 지정이 최우선.**
2. **기존 원고 수정 작업**이면 **원문 종결어미 보존이 기본값.** 변경은 사용자가 요청했을 때만.
3. **새 글 작성**이면 채널 기본값: 에세이·개인 블로그 → ~다체 / 비즈니스 문서·보고서·이메일 → ~습니다체 / 발표 슬라이드 → 개조식.
4. 한 문서 안에서 어미를 섞지 않는다 (H3).

### 7.4 편집자 역할 전환 선언

리라이팅·검수 단계 진입 시 내부적으로 다음을 선언하고 관점을 전환한다 (출력에 노출하지 않음):

> "지금부터 작성자가 아니라 편집자로서 점검한다. 기준: ① 독자가 첫 문단에서 계속 읽을 이유가 있는가 ② 각 문단이 제 역할을 하는가 ③ H1~H6 통과 ④ 금지어(§7.1) 잔존 여부 ⑤ 어미·톤 일관성(§7.3)."

## 8. 작업 규모 3급 분류와 분할

착수 전에 작업 규모를 판정하고 규모에 맞는 전략을 고른다. 한 번에 통짜로 만들 수 없는 작업을 통짜로 시도하는 것이 장기 작업 품질 저하·중단·컨텍스트 유실의 최대 원인이다.

### 8.1 3급 분류

| 급 | 정의 | 예 | 실행 전략 |
|---|---|---|---|
| **S 단발형** | 1세션 안에 끝나는 단일 산출물, 본문 7,000자 이내 | 짧은 글, 이메일, 대본 1편, 요약 | 단일 실행. 분할 오버헤드가 손해 — §4 하네스만 적용 |
| **L 장문형** | 단일 산출물이지만 분량이 큼. 9,000자 이상 또는 슬라이드 15장 이상 | 슬라이드 덱, 책 챕터 묶음, 긴 제안서, 다중 섹션 페이지 | 단락 분할 + 서브에이전트 위임 (§8.2) |
| **D 지속개발형** | 파일 트리(코드베이스)가 남고 여러 세션에 걸쳐 개발·수정이 이어짐 | 앱 기능·유지보수, 사이트 수정, 자동화 시스템 구축 | 브랜치 격리 + 기능 단위 분해 (§8.3) |

**판정 3문**: ① 산출물이 분할 기준(9,000자 / 15장)을 넘는가 → L 이상. ② 산출물이 코드베이스이고 이번 이후에도 수정이 이어지는가 → D. ③ 둘 다 아니면 S. 애매하면 S로 시작하되, 실행 중 분량 초과가 보이면 그 자리에서 승급한다. 지금까지의 산출물·구조를 저장한 뒤 분할 모드로 재개하고, 통짜로 강행하지 않는다.

### 8.2 장문형(L) — 단락 분할·위임

1. **뼈대 먼저**: 전체 구조(목차·섹션 목록)를 메인이 먼저 확정하고 파일로 저장한다. 이 뼈대가 모든 분할 단위의 기준선이다. 뼈대 없이 단락부터 쓰지 않는다.
2. **위임 단위**: 1위임 = 1단락. 한 에이전트가 한 번에 완주할 수 있는 크기로 자른다 (본문 7,000자 / 슬라이드 3~5장 / 섹션 1개 / 챕터 1개).
3. **병렬 vs 순차**: 독립 단락(카드·섹션·슬라이드 그룹)은 병렬. 문체가 민감한 단락(연속 서사·에세이·챕터 본문)은 순차로 하고 직전 산출물을 동봉한다.
4. **단락마다 저장**: 각 단락 완료 시 저장한다. 세션이 끊겨도 완료 단락은 재작업하지 않는다.
5. **병합은 메인**: 단락 병합, 톤 드리프트(H3), 단락 간 중복(H4), 전체 일관성 검수는 메인 책임이다.

### 8.3 지속개발형(D) — 격리·기능 단위 분해

1. **브랜치 격리**: git 저장소면 기본 브랜치에서 직접 작업하지 않는다. 작업 단위 브랜치를 만들고, 파일을 수정하는 에이전트를 병렬로 돌릴 때는 에이전트별 작업 트리로 격리한다.
2. **나노 작업 분해**: "앱 만들어줘"를 통째로 위임하지 않는다. 화면 1개·모듈 1개·기능 1개 단위로 위임하고, 각 위임에 완료 기준(빌드·테스트·린트 통과)을 명시한다. 완료 판정의 상세 규율은 dev-evidence-gate를 따른다.
3. **분해 축 선택**: 기능 축(기능 1개 = 에이전트 1기, 기본값)과 역할 축(디자인 / 프론트엔드 / 백엔드 레이어별 1기)이 있다. **역할 축으로 병렬할 때는 착수 전에 레이어 간 인터페이스 계약(API 스키마·데이터 모델·디자인 토큰)을 메인이 먼저 고정해 각 위임에 동봉한다.** 계약 없이 레이어를 병렬로 돌리면 병합 시 인터페이스가 어긋난다.
4. **병합은 메인 소유**: 에이전트가 직접 기본 브랜치에 병합하지 않는다. 메인이 순서대로 병합하고 통합 빌드·테스트를 돌린 뒤 다음 라운드로 간다.
5. **세션 경계**: 세션을 끝내기 전 반드시 커밋한다. 다음 세션은 브랜치와 진행 상태 파일에서 재개한다.

## 9. 위임 계약 (서브에이전트를 쓸 때)

작업을 서브에이전트에 넘길 때 위임 프롬프트에 아래를 모두 담는다. 빠지면 자식이 배회하거나 엉뚱한 산출물을 낸다.

1. **역할 선언** — 무엇을 하는 담당인지 한 줄.
2. **참조 문서 경로** — 따라야 할 절차 문서가 있으면 경로를 주고 "읽고 수행하라"고 지시한다. 내용을 프롬프트에 통째로 붙여넣지 않는다.
3. **입력 위치와 읽을 항목** — 컨텍스트 파일 경로 + 그 단계가 읽을 키 목록.
4. **산출물 저장 경로** — 본문을 대화로 반환하지 말고 파일로 저장하게 한다.
5. **반환 계약** — 요약·체크리스트·플래그만 반환. 누락·불확실은 `missing_inputs`로.
6. **사용자 직접 질문 불가 고지** — 자식은 사용자에게 못 묻는다. 막히면 플래그로 반환하고 메인이 묻는다.
7. **완료 조건(STOP WHEN)** — 실행을 끝내는 관찰 가능한 조건 한 줄.

추가 원칙:

- **작성자와 검수자를 분리한다.** 생성 에이전트의 산출물을 별도 검수 에이전트가 §4로 점검하게 한다. 검수 과정은 노출하지 않고 반영된 결과만 사용자에게 보인다.
- **재위임 금지 고지**: 위임 프롬프트 첫 줄에 "너는 실행 담당이다. 추가 위임 금지, 직접 수행하라"를 넣어 재귀 위임을 막는다.
- **수정 루프**: 수정 요청이 오면 새 에이전트를 만들지 말고 동일 에이전트에 수정 지시를 이어 보낸다(컨텍스트 보존).
- **병렬은 독립 단위만.** 전역 제약(톤 일관성·전체 분량 배분)이 있는 단계는 단일 에이전트를 유지한다.

## 10. 적용 보고

스킬이나 공통 표준을 적용해 산출물을 만든 작업은, 최종 요약 끝에 **무엇을 어떤 기준으로 적용했는지** 짧게 보고한다. 사용자가 적용 여부를 직접 검증할 수 있게 하기 위함이다.

```
**적용 표준:**
- work-harness §4 — H5 정밀도로 "빠른 시일 내"를 "3영업일 내"로 교체
- work-harness §7.2 — 본문 긴 하이픈 4곳 제거
```

규칙:

1. **실제 반영분만 쓴다.** 읽기만 하고 결과물에 반영되지 않은 항목은 쓰지 않는다 (H6).
2. **결과 중심 1줄.** 절차 나열이 아니라 "이 산출물의 어느 부분이 그 표준으로 바뀌었는지"를 쓴다.
3. 내부 검수 왕복 과정은 계속 비노출하되, 어떤 표준이 적용됐는지 **결과**는 보고한다.
4. 표준이 하나도 관여하지 않은 단순 응답에는 붙이지 않는다.
