# App Launch Pipeline — 아이디어에서 스토어까지

> 아이디어 한 줄을 주면 MVP 범위가 확정된 기획안 → 화면 설계 → 동작하는 앱 → 검증 증거 → 스토어 출시 패키지까지 이어진다. 이 스킬의 값어치는 5단계를 나눈 데 있지 않고, **각 단계에서 무엇을 확정해야 다음으로 넘어갈 수 있는지**를 게이트로 못 박은 데 있다.

## 0. 전제와 원칙

### 0.1 이 스킬 하나로 끝난다

**다른 스킬이 없어도 5단계 전 과정이 돌아간다.** 본문의 게이트·체크리스트가 그 자체로 완결돼 있고, 외부 스킬 연계는 §11의 **선택 사항**이다. 같은 저장소의 `dev-evidence-gate`·`work-harness`를 함께 깔면 검증·검수가 자동으로 물리지만, 안 깔아도 §11에 같은 내용의 인라인 체크리스트가 있다.

### 0.2 준비물

처음 앱을 내는 사람이 **여기서 제일 많이 막힌다.** STEP 1을 시작하기 전에 확인한다.

| 시점 | 필요한 것 | 비고 |
|---|---|---|
| STEP 1~2 | 없음 | 기획·디자인은 도구 없이 대화만으로 진행된다 |
| STEP 3부터 | **JDK 17+**, **Android Studio**(SDK·에뮬레이터 포함) | 설치는 사용자가 직접 한다(관리자 권한 필요) |
| STEP 4부터 | **안드로이드 실기기 1대** + USB 케이블, USB 디버깅 켜기 | 에뮬레이터만으로는 검증이 끝나지 않는다(§6) |
| STEP 5 | **구글 플레이 개발자 계정** | 등록비 **$25 1회**(환불 없음). 개인 계정은 승인에 며칠 걸릴 수 있고, 별도 테스터 요건이 붙는 경우가 있다 |
| STEP 5 | 개인정보처리방침을 올릴 **웹 주소 한 개** | 정적 호스팅 무료 등급이면 충분하다(§8.1) |

> **계정 심사는 앱 심사와 별개다.** 개발자 계정 승인이 안 나면 앱을 다 만들어 놓고도 올릴 곳이 없다. STEP 3에 들어가는 시점에 계정 등록을 **병행해서 걸어 두는 편이 낫다.** 대기 시간을 개발 시간에 겹쳐 태우는 것이다.

빌드 환경이 없는 상태로 STEP 3 진입을 요청받으면, **설치 안내까지만 하고 멈춘다.** 설치가 끝났는지 확인한 뒤 진행한다.

### 0.3 원칙

사용자는 **PM**, AI는 **개발 책임자**다. PM이 개발상 잘못된 지시를 내리면 근거를 들어 바로잡는 것까지가 책임이다. "시키는 대로 했더니 안 되더라"는 결과를 만들지 않는다.

1. **합의 모드** — 각 단계 산출물을 사용자가 컨펌해야 다음으로 넘어간다. 특히 STEP 1(MVP 범위)과 STEP 5(스토어 공개)는 되돌리기가 비싸므로 반드시 멈춘다.
2. **컨텍스트 누적** — `carry`를 단일 진실원으로 들고 단계마다 갱신·주입한다. 앱 하나는 한 세션에 안 끝난다.
3. **상류에서 좁힌다** — 신규 앱 실패의 최빈 원인은 **범위 폭주**다. STEP 1에서 "v1.0에서 뺄 것"을 기능 목록만큼 구체적으로 확정하고, 개발 중 기능 추가 요청이 오면 그 목록을 근거로 다음 버전 백로그로 보낸다.
4. **완료 = 기기 동작 확인** — "빌드 성공"은 완료가 아니다. 에뮬레이터·실기기의 logcat·스크린샷 증거로만 완료를 선언한다(§6, §11).
5. **정책은 기획 단계부터** — 스토어 정책 리스크(권한·민감 카테고리·포그라운드 서비스)는 출시 직전에 처음 보는 게 아니라 STEP 1에서 스캔해 `carry.policy_risks`로 끌고 다닌다.

## 1. 파이프라인 흐름

```
[아이디어] → [진행 상황 확인 — 새 앱인가 이어가기인가]
    │
    ├─ 【도구 불필요】 대화만으로 진행
    │   [STEP 1] 기획   → 기획안(MVP 범위·정책 리스크)   ──합의──▶
    │   [STEP 2] 디자인 → 화면 설계·디자인 토큰           ──합의──▶
    │
    └─ 【로컬 개발 환경 필요】 여러 세션에 걸침
        [STEP 3] 개발   → 동작하는 앱(마일스톤별 빌드 게이트) ──합의──▶
        [STEP 4] 검증   → 기기 동작 증거·정책 점검 리포트     ──합의──▶
        [STEP 5] 출시   → 스토어 패키지·서명 AAB·Play Console ──합의──▶
```

위 묶음은 **필요한 환경** 기준이다. 실제 세션을 어디서 끊는지는 §9의 표를 따른다(둘은 경계가 다르다).

STEP 2와 STEP 3 사이가 진짜 경계다. **여기서부터는 되돌리는 값이 급격히 비싸진다.** 화면 설계를 텍스트로만 훑고 넘어가지 말 것.

## 2. 컨텍스트 (carry)

```yaml
master_context:
  app:
    name: ""               # step1 후보 → step5 확정 (스토어 표기명)
    application_id: ""     # step1 후보 → step3 스캐폴딩에서 확정 (이후 변경 불가)
    src_dir: ""            # step3 — 프로젝트 루트 절대경로
  carry:
    concept_promise: ""    # step1 — 사용자가 무엇을 얻는가, 결과 동사형 한 줄
    target: ""             # step1 — 누가 쓰는가 (상황·빈도까지)
    core_features: []      # step1 — 3~5개, 각각 완료 기준 포함
    out_of_scope: []       # step1 — v1.0에서 명시적으로 뺀 것 (범위 폭주 방어의 근거)
    revenue_model: ""      # step1
    policy_risks: []       # step1 발굴 → step4 재점검
    name_candidates: []    # step1 → step5 확정
    screens: []            # step2 — 화면 목록·흐름(id·기능 매핑)
    design_tokens: {}      # step2 — 컬러·타이포·컴포넌트 규칙
    milestones: []         # step3 — 구현 순서·완료 여부
    repo: ""               # step3 — git 원격 주소 (없으면 "local only")
    verify_evidence: []    # step4 — 기능별 logcat·스크린샷 증거
    listing: {}            # step5 — 제목·설명·키워드·데이터 보안 양식
    web_presence: {}       # step5 — 개인정보처리방침 URL 등
    version: { name: "1.0", code: 1 }

accumulation_rule:
  - "각 단계 종료 시 신규 필드를 carry에 머지(기존 값 보존)."
  - "다음 단계 시작 시 carry 전체를 주입한다."
  - "개발 중 기능 추가 요청 → out_of_scope 대조 후 백로그 제안. carry 수정은 사용자 합의로만."
  - "단계 게이트 통과 전에 그 단계 소관 필드가 전부 채워졌는지 확인한다. 빈 필드는 게이트 미통과다."
```

**단계별 소관 필드** — 게이트에서 이 목록으로 대조한다.

| 단계 | 채워야 할 필드 |
|---|---|
| STEP 1 | `app.name`(후보) · `app.application_id`(후보) · `concept_promise` · `target` · `core_features` · `out_of_scope` · `revenue_model` · `policy_risks` · `name_candidates` |
| STEP 2 | `screens` · `design_tokens` |
| STEP 3 | `app.application_id`(확정) · `app.src_dir` · `milestones` · `repo` |
| STEP 4 | `verify_evidence` · `policy_risks`(해소 표시) |
| STEP 5 | `app.name`(확정) · `listing` · `web_presence` · `version` |

`carry`를 파일로 남기면(`.claude/pipeline/<app>_context.json` 등) 세션이 끊겨도 이어갈 수 있다. 매 세션 시작 시 이 파일을 먼저 읽고 "지금 몇 단계"를 보고한다.

## 3. STEP 1 — 기획 · 합의 정지점

**입력**: 아이디어 한 줄이면 충분하다. 구체화가 이 단계의 일이다.

**산출물**

- `concept_promise` — "이 앱으로 사용자가 무엇을 얻는가"를 결과 동사형 한 줄로. 형용사 금지.
- `target` — **누가, 어떤 상황에서, 얼마나 자주 쓰는가.** "20~30대"는 타깃이 아니라 인구통계다. 사용 상황이 안 나오면 STEP 2에서 화면 흐름을 정할 근거가 없고, STEP 5에서 리스팅 첫 문단의 `[대상]` 자리를 채울 수 없다.
- **시장·경쟁 스캔** — 스토어 동종 앱 3~5개. 별점이 아니라 **리뷰의 불만 지점**을 본다. 그게 차별 기회다. 불만 항목마다 리뷰 원문 1문장과 URL을 붙인다(도메인 나열만으로는 검증할 수 없다).
- `core_features` 3~5개 — 각각 **완료 기준**을 함께 적는다.
- `out_of_scope` — **핵심 기능만큼 구체적으로.** "나중에 할 것들"은 목록이 아니다.
- `revenue_model` — 없으면 없다고 적는다.
- `policy_risks` 사전 스캔 — 필요 권한 목록, 민감 카테고리 해당 여부, 포그라운드 서비스 사용 여부, 타깃 SDK 마감일. **현재 요건을 웹에서 확인한다**(매년 바뀐다).
- `name_candidates` 3개 + applicationId 후보(역도메인 컨벤션).

**게이트**

- [ ] `concept_promise`가 한 줄로 확정됐다
- [ ] `target`에 사용 상황이 들어 있다 (인구통계만 있으면 미통과)
- [ ] `out_of_scope`가 `core_features`만큼 구체적이다
- [ ] `policy_risks`에 권한·카테고리 근거가 있다
- [ ] 경쟁 스캔이 추측이 아니라 검색 근거를 갖는다

**정지**: 기획안 **전문**을 최종 형태로 제시하고 컨펌받는다. 요약만 주고 넘어가지 않는다 — 설계 산출물은 코딩 전에 최종 형태로 확인해야 값이 싸다.

> 💡 이 단계에서 기능이 잘려나가는 게 정상이다. 사용자가 "이것도 넣고 싶다"고 적은 것 중 서버·회원가입·외부 연동이 필요한 항목은 대개 v1.0에서 빠진다. **버리는 게 아니라 다음 버전 목록으로 옮기는 것**임을 명시해야 합의가 쉽다.

## 4. STEP 2 — 디자인 · 합의 정지점

**산출물**

- **화면 목록** — 모든 `core_feature`가 화면에 매핑돼야 한다(누락 0). 화면마다 id·목적·진입 경로.
- **화면 흐름도**(텍스트) + **화면별 와이어프레임** — 구성 요소와 함께 **빈 화면·권한 거부·오류 상태**까지.
- `design_tokens` — 컬러·타이포·컴포넌트 규칙. Material 3 기본.
- 아이콘·그래픽 컨셉 — 생성은 STEP 5에서.

**게이트**

- [ ] `core_features` 전부 화면에 매핑됨
- [ ] 핵심 기능 도달이 **3탭 이내**(유틸 앱 원칙)
- [ ] 빈 화면·권한 거부·오류 상태가 설계됨
- [ ] **장시간 작업에 무한 진행 표시가 없다** — 외부 SDK 다운로드 등은 타임아웃 → 실패 → 재시도 상태까지 설계
- [ ] `out_of_scope` 기능의 화면이 섞여 있지 않다

**정지**: 텍스트 와이어프레임만으로 컨펌받지 않는다. **시각 목업**(HTML 한 장이면 충분 — 폰 프레임, 확정 토큰 적용, 핵심 화면 + 엣지 상태)을 만들어 보여준 뒤 컨펌받는다. 코드 구현 후 수정보다 목업 수정이 훨씬 싸다.

## 5. STEP 3 — 개발 · 로컬 전용 · ⚠️ timeout 최고 위험

**절차**

1. **스캐폴딩** — Kotlin/Gradle 프로젝트 생성. 이 단계에서 반드시 함께 하는 것 셋:
   - `.gitignore`에 **서명 자산 선차단** — `*.jks` `*.keystore` `*.pepk` `keystore.properties` `local.properties`. 커밋 전 스테이징 누출 검사를 습관으로.
   - **edge-to-edge 인셋 패딩을 전 화면에** — targetSdk 35+는 edge-to-edge가 강제다. 빠뜨리면 하단 버튼이 제스처 내비게이션에 깔리는데, **에뮬레이터에서는 안 보이고 실기기에서만 드러난다.**
   - **`.dev` 변종을 지금 붙인다**(§7 참조). 나중에 붙이면 다시 해야 할 등록 작업이 줄줄이 나온다.

   스캐폴딩이 끝나면 **`app.application_id`(확정)·`app.src_dir`(프로젝트 루트 절대경로)·`carry.repo`를 즉시 기록한다.** applicationId는 스토어에 한 번 올라가면 **영구히 못 바꾼다.** 여기가 마지막 확정 시점이다. git 원격을 안 만들 거면 `repo: "local only"`로 명시한다 — 빈 값은 "아직 안 정함"과 구분되지 않는다.
2. **마일스톤 수립** — 화면 골격 → 핵심 기능(`core_features` 순) → 부가(광고·설정). `carry.milestones`에 기록.
3. **마일스톤 게이트** — `./gradlew assembleDebug` 통과 + 해당 기능 에뮬레이터 스모크 → 커밋. 커밋 메시지에 **무엇을·왜·어떻게 검증했는지**.
4. **범위 방어** — 구현 중 기능 추가 요청이 오면 `out_of_scope`와 대조하고 백로그를 제안한다. 즉시 구현하지 않는다.

**게이트**

- [ ] 전 마일스톤 `assembleDebug` 통과
- [ ] 서명 자산 스테이징 누출 0
- [ ] `out_of_scope` 침범 0
- [ ] `app.application_id`·`app.src_dir`·`carry.repo` 기록됨

> 🔴 **앱 하나를 한 호출에 만들지 않는다.** 마일스톤 단위(세션당 1~2개)로 쪼개고 매번 `carry`에 진행을 기록한다. 대량 보일러플레이트 생성과 긴 빌드 로그는 별도 서브에이전트가 흡수하게 해 메인 컨텍스트를 아낀다.

## 6. STEP 4 — 검증 · 로컬 전용

**"빌드 성공"은 증거가 아니다.** `core_features` 각각을 실제로 태워 logcat·스크린샷을 `carry.verify_evidence`에 남긴다.

**에뮬레이터로 충분한 것** — 빈 상태, 온보딩, 미설치 폴백 같은 자족 시나리오.

**실기기가 필수인 것** — 외부 앱 연동(딥링크·인텐트), 실환경 의존 기능(위치·지오코더), 그리고 **UI 인셋**. 에뮬레이터 통과는 검증 완료가 아니다. 실기기에서만 드러나는 버그 클래스가 실제로 있다:

- edge-to-edge 인셋·제스처 영역 겹침
- 자판이 입력창을 가려 입력 중인 글자가 안 보임
- RadioGroup을 감쌌을 때 상호배타 실패
- 외부 SDK 다운로드가 조용히 멈춤

**엣지 검증** — STEP 2에서 설계한 빈 화면·권한 거부·오류 상태 + 프로세스 킬 후 복귀. 외부 SDK 무한 대기 지점은 워치독 동작(타임아웃 → 재시도 UI)까지 실측한다.
*구현 주의*: 블로킹 호출에 협조적 취소(`withTimeout`)는 무력하다. 분리된 스코프 + 호출자 측 타임아웃으로 처리하고 `CancellationException`을 삼키지 않는다.

**정책 점검** — 최신 요건을 웹에서 확인한 뒤 매니페스트 권한 최소화·FGS 타입·타깃 SDK·데이터 수집 항목을 대조한다. STEP 1의 `policy_risks` 전 항목이 해소됐는지 확인.

**릴리스 빌드 예행** — `./gradlew bundleRelease`로 minify·리소스 이슈를 미리 발견한다.

**게이트**

- [ ] `core_features` 전부 기기 동작 증거 있음
- [ ] `policy_risks` 전 항목 해소
- [ ] 스모크 기준 크래시 0
- [ ] 릴리스 빌드 통과

## 7. `.dev` 변종 — 폰을 지우지 않고 확인하는 법

STEP 3 스캐폴딩에서 미리 붙여 두는 장치다. 이유가 셋이다.

1. **스토어 설치본은 로컬 빌드로 덮을 수 없다.** 스토어 앱은 구글이 서명하기 때문이다.
2. **덮으려고 지우면 그 앱의 실사용 데이터가 같이 날아간다.** 본인이 실제로 쓰는 앱이면 치명적이다.
3. **스토어 내부 테스트로 확인하는 루프는 성립하지 않는다.** 폰까지 전파되는 데 10~30분이 걸린다. 버그 하나 보려고 쓸 시간이 아니다.

해법은 debug 빌드에 `applicationIdSuffix '.dev'`와 `versionNameSuffix '-dev'`를 붙여 **스토어본과 나란히 깔리게** 만드는 것이다. 런처 이름은 `src/debug/res`에서 덮어 구분한다. 진짜 앱은 손대지 않고 연습용에서만 확인하면 되고, 확인은 10초면 끝난다.

> **나중에 붙이면 비싸다.** 애널리틱스·크래시 리포팅을 붙였다면 콘솔에 앱을 다시 등록하고 설정 파일을 재발급받아야 한다. 그래서 스캐폴딩 단계에 넣는다.

## 8. STEP 5 — 출시 · 합의 정지점

### 8.1 스토어 리스팅

- **앱 이름**(30자) — 상표·동명 앱·다른 의미 혼재를 웹으로 확인한 뒤 확정.
- **짧은 설명**(80자), **전체 설명** — **실기능만.** 과장 금지. "오프라인 동작" 류를 쓸 때는 초회 다운로드·광고 통신 조건을 명시한다.
- **검색·AI 노출** — 전체 설명 첫 문단을 `[앱 이름]은 [대상]이 [문제]를 [방식]으로 해결하는 앱`이라는 **자족 문장**으로 시작한다. AI 검색 답변에 그대로 발췌되는 자리다. 키워드는 전통 검색어와 **대화형 질의**("사진 소리 안 나게 하는 법?" 류) 3~5개를 각각 커버한다.
- **개인정보처리방침 URL** — Play Console 필수다. 유료 호스팅이 필요 없다. 정적 호스팅 무료 등급에 페이지 하나면 된다.
- **스크린샷·그래픽 자산** — **실존 화면만.** 없는 화면을 그린 플랜은 반려한다. 필수 자산은 아이콘 512·피처 그래픽 1024×500, 그리고 스크린샷 **3종**이다.

  > 🔴 **폰만 만들면 등록정보 저장이 막힌다.** 폰 + **7인치 태블릿** + **10인치 태블릿**이 전부 필수(\*)다(실측). 태블릿 AVD를 따로 만들 필요는 없고 폰 에뮬레이터의 해상도·밀도만 바꿔 찍으면 된다. 또 요즘 폰 원본(1080×2400 = 2.22:1)은 **비율 규격 위반**이라 그대로 올라가지 않는다.

  생성·합성·검증 절차 전체는 `references/store-screenshots.md`에 있다. **STEP 5에 들어가면 이 파일을 먼저 읽는다.**

### 8.2 데이터 보안 양식

**실제 수집 항목과 1:1이어야 한다.** 과잉 신고도 문제다.

- 기기 안에서 처리·저장만 하고 밖으로 안 보내는 데이터는 구글 정의상 **'수집'이 아니다.**
- 광고 SDK를 넣었다면 광고 ID는 네 필드를 명시한다 — 수집=예 / 제3자 공유=예 / 목적=광고 / 필수(거부 불가).

### 8.3 서명과 업로드

- **새 keystore 생성 → 3중 백업**(로컬·외장·클라우드). **비밀번호는 파일에 저장하지 않는다.** 백업이 끝나기 전에는 업로드하지 않는다. 이 키를 잃으면 그 앱은 영원히 업데이트할 수 없다.
- 서명 AAB 빌드 → Play Console 새 앱 등록(Play App Signing) → 내부 테스트 → 프로덕션.
- **스토어 공개·심사 제출은 되돌릴 수 없는 외부 공개 행위다.** 반드시 사용자 확인 후에만 실행한다.

### 8.4 🔴 출시에서 막히는 자리 다섯 곳

절차대로 했는데도 앱이 안 나가는 상황은 대개 아래 다섯 중 하나다. **미리 알고 있어야 사흘을 안 버린다.**

| # | 함정 | 실제로 일어나는 일 |
|---|---|---|
| 1 | **검토 제출 ≠ 출시** | 제출 버튼을 눌러도 앱 자체는 **초안** 상태로 남아 있을 수 있다. 트랙에 번들이 올라간 것과 앱이 출시된 것은 다른 상태다 |
| 2 | **'검토를 위해 앱 전송' 버튼이 비활성** | 앱 콘텐츠 선언이 안 끝난 것이다. **데이터 보안 양식·콘텐츠 등급·개인정보처리방침 URL** 셋을 다 채워야 버튼이 살아난다 |
| 3 | **이 상태는 API로 안 보인다** | Play Developer API는 트랙에 번들을 올리는 데까지다. **검토 제출과 게시는 API에 없다** — 콘솔에서 사람이 눈으로 확인해야 한다 |
| 4 | **대시보드 진행도는 트랙별이다** | 프로덕션·공개·비공개 카드가 각각 다르다. 하나 보고 전체 상태로 오해하기 쉽다 |
| 5 | **versionCode는 소모품이다** | 한 번 올라간 번호는 **재사용할 수 없다.** 태그 push로 배포되는 CI를 붙였다면 시험 삼아 민 태그 하나가 번호를 영구히 먹는다 |

**5번 대응** — CI를 붙일 때 "평소 push는 빌드·검증만, 배포는 특정 신호(릴리스 태그)일 때만"으로 반드시 나눈다. 앱 코드가 한 글자도 안 바뀌었는데 번호만 사라지고, 그 뒤 배포에서 버전 충돌로 시간을 더 쓴다.

> 또 하나 — **첫 설치에서만 나는 버그**는 개발자가 자기 폰으로 절대 못 잡는다. 첫 실행 경로에서 화면들이 서로를 띄우며 스스로 빠지면 마지막 화면이 태스크 루트가 되고, 거기서 '닫기'를 누르면 앱이 통째로 종료된다. `isTaskRoot`일 때 부모 화면을 먼저 띄우는 처리를 넣고, **앱 데이터를 지운 상태에서 반드시 한 번 검증한다.** §7의 `.dev` 변종이 여기서 값을 한다.

### 8.5 게이트

- [ ] 리스팅과 실기능 일치 (과장·미구현 기능 언급 0)
- [ ] **스크린샷 3종(폰·7인치·10인치) 전부 준비됨** + 아이콘 512 + 피처 그래픽 1024×500
- [ ] 전 이미지 비율·최소변 규격 자체검증 통과 (`references/store-screenshots.md` 체크리스트)
- [ ] 개인정보처리방침 URL이 실제로 열린다
- [ ] 데이터 보안 양식 = 실제 수집 항목 일치

## 11. 확장 (선택) · 없이도 돌아간다

이 절은 **전부 선택 사항이다.** 아래 스킬이 하나도 없어도 §0~§10만으로 앱은 나간다.

### 11.1 다른 스킬을 함께 깔았다면

같은 저장소(`public-skills-repo`)의 스킬이 설치돼 있으면 자동으로 물린다.

- **`dev-evidence-gate`** — 코드가 나오는 STEP 3~4에 적용한다. 시나리오 계약·증거 2종·정리 영수증이 이 스킬의 "기기 동작 증거" 요구를 구체화한다.
- **`work-harness`** — 기획안·리스팅 카피·개인정보처리방침처럼 **읽는 산출물**을 출력 전에 점검한다.

### 11.2 없을 때 쓰는 인라인 체크리스트

위 스킬 없이 진행할 때는 이 두 묶음을 해당 단계에서 직접 적용한다. **산출물 품질은 같아진다.**

**코드 산출물 (STEP 3~4에서)**

- [ ] 착수 전에 통과 조건을 **이진 관찰 가능한 문장**으로 적었다. "잘 동작해야 함"은 조건이 아니다. "녹음 버튼을 누르면 3초 안에 파일이 `/files/rec/`에 생긴다"가 조건이다
- [ ] 고치기 **전에** 실패를 한 번 재현해 남겼다 (실패를 못 본 수정은 뭘 고쳤는지 모르는 수정이다)
- [ ] 실제 화면에서 직접 눌러 봤다. 빌드 로그·테스트 통과는 증거가 아니다
- [ ] 검증하느라 띄운 에뮬레이터·프로세스·임시 파일을 껐거나, 살려 둔 이유를 적었다
- [ ] 같은 실패를 **2번** 같은 방법으로 고치려 하지 않았다. 2번 막히면 접근을 바꾸고, 3번이면 되돌린다
- [ ] 통과 조건이 성립하면 **거기서 멈췄다.** 그 뒤의 추가 리팩터링은 범위 초과다

**읽는 산출물 (STEP 1·2·5에서)**

- [ ] 사용자가 요청한 항목이 **하나도 빠지지 않았다**
- [ ] 그대로 복사해 Play Console에 붙여넣을 수 있다. "여기에 앱 설명을 넣으세요" 같은 자리표시자가 없다
- [ ] 앞뒤 문단이 서로 어긋나지 않는다
- [ ] 사실과 추정이 구분돼 있다. 정책·규격처럼 **바뀌는 값은 확인한 날짜와 출처**를 붙였다
- [ ] 과장형 형용사("혁신적인", "매우 효과적인")와 근거 없는 단정이 없다. 리스팅 카피에서는 이게 **정책 위반으로 직결된다**

### 11.3 서브에이전트 (있는 환경에서만)

STEP 1·2·5는 판단형이라 작성/검수를 나눠 맡기면 이득이 있다. STEP 3~4는 로컬 빌드·기기에 강결합된 도구형이라 직접 실행하는 편이 낫다. **위임은 최적화이지 필수가 아니다.** 서브에이전트가 없으면 같은 체크리스트를 인라인으로 적용하면 되고, 산출물은 동일하다.

## 부록. 이 스킬의 출처

실제로 앱을 기획부터 구글 플레이 출시까지 끌고 가면서 막힌 자리를 그때그때 절차로 옮겨 적은 결과물이다. §7(`.dev` 변종)·§8.4(출시에서 막히는 자리)·§6(실기기에서만 드러나는 버그 클래스)은 전부 문서를 읽고 정리한 게 아니라 **실제로 당하고 나서** 추가된 항목이다.

그래서 이 스킬의 값어치는 5단계 구조가 아니라 그 안에 박힌 게이트에 있다. 구조는 누구나 그릴 수 있지만, "검토 제출 버튼을 눌렀는데 왜 앱이 안 나가는가"는 사흘을 버려 봐야 알게 된다.
